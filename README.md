# ورد الروضة

> **حالة الحوكمة (`GD-G0-FINAL`):** G0 معتمدة/مغلقة/مجمدة، وG1 مفتوحة، وG2–G12 غير مفتوحة. ما يرد أدناه عن «مراحل مكتملة» أو وظائف prototype ليس دليل اجتياز Gate. النطاق المعتمد مؤسسي ومحدود وفق `G0_FROZEN_BASELINE.md`. غياب حالة الإنتاج `NOT VERIFIED` وأي rebuild هدّام ممنوع.

منصة عربية تساعد المستخدم على بناء ورد يومي ثابت من القرآن والأذكار، ومتابعة إنجازه بهدوء ومن دون تعقيد.

> **افتراض تأسيسي:** أُنشئت هذه الوثائق اعتمادًا على اسم المشروع فقط. النطاق مبدئي وقابل للتعديل، بينما تعتمد التقنية الحالية Flutter وSupabase والحزم المذكورة أدناه.

## ما الذي يقدمه المنتج؟

- إنشاء ورد يومي من القراءة والأذكار.
- عداد ذكر خاص يعمل دون اتصال ويحفظ التقدم ويزامنه بأمان.
- عرض مهام اليوم في شاشة واحدة.
- تسجيل الإنجاز والتقدم الجزئي.
- تذكيرات اختيارية وفق المنطقة الزمنية للمستخدم.
- سجل مبسط للاستمرارية والإنجاز.
- إدارة المؤسسات والفروع والصفوف ومستخدمي الفروع للمدير المخول.

## حالة المشروع

اكتملت المراحل الثانية والثالثة والرابعة والخامسة والسادسة:

- تسجيل الدخول بالبريد وكلمة المرور عبر Supabase Auth.
- استعادة Session ومراقبة تغيراتها عبر Riverpod.
- دورا `member` و`admin` محفوظان في جدول `profiles` المحمي بـRLS.
- توجيه `member` إلى `/home` و`admin` إلى `/admin` مع منع الدور غير المعروف افتراضيًا.
- اختبارات لإدارة الجلسة وتحديد الدور وحماية المسارات والتحقق من نموذج الدخول.
- إدارة `Organization → Branch → Class → Child` من لوحة المدير.
- CRUD كامل بالحذف الناعم، وعضوية إدارية مستقلة لكل مؤسسة.
- اختبار سيناريو إنشاء «فرع دمشق»، ثم صف داخله، ثم إضافة طفل إلى الصف.
- CRUD للطفل والمعلم والإداري ومدير الفرع، مع ربط كل مستخدم بفرع.
- ربط الطفل والمعلم بصف إلزامي، وربط الإداري ومدير الفرع بالفرع دون صف.
- شاشة `DhikrScreen` لإنشاء عداد خاص بهدف يحدده المستخدم.
- حفظ كل ضغطة محليًا عبر Drift، وحالة اكتمال عند بلوغ الهدف دون تجاوزه.
- طابور مزامنة بمعرّف ثابت لكل زيادة وRPC تمنع احتساب العملية مرتين.
- إدارة أوراد الفروع بدورة `إنشاء → تعديل → تكليف → إنهاء`.
- لا يقبل الورد التكليف إلا لمستخدم نشط في الفرع نفسه، ولا يتغير بعد الإنهاء.
- رحلة طفل مبسطة: `Login → Home → وردي اليوم → العداد → الإتمام → النقاط/الشارة`.
- تحتوي Home الطفل ثلاثة أقسام فقط: «وردي»، «إنجازاتي»، و«مكافآتي»، دون قوائم إدارية أو إعدادات معقدة.
- رحلة موظف مبسطة: `Login → وردي → العداد → تقدمي → السجل`.
- يظهر قسم «صفي» للمعلم المرتبط بصف فقط، ويقتصر على الصف وأطفاله عبر RLS.
- تبدأ لوحة مدير الفرع بمؤشرات اليوم: المشاركون، المكتملون، النسبة، إجمالي الأذكار، الأطفال والموظفون المشاركون.
- تعرض اللوحة مداخل `Users`, `Classes`, `Wirds`, `Campaigns`, `Reports`, و`Rewards`؛ ويتضمن Reports تقرير الإنجاز ومؤشرات النزاهة الإدارية.
- يدعم تقرير الإنجاز دمج فلاتر الفترة والفرع والصف والدور والمستخدم والورد والذكر وحالة الإتمام، وتُطبق جميعها خادميًا ضمن المؤسسة المصرح بها.
- يتضمن MVP ثلاثة عروض للتقارير: ملخص يومي، وتقرير فرع بعد اختياره، وتقرير مستخدم بعد اختياره. التقارير الأسبوعية والشهرية والمقارنات والتصدير مؤجلة لما بعد MVP.
- تعرض لوحة الإدارة المركزية مقارنة يومية لكل فروع المؤسسة، مع فلتر «كل الفروع» أو فرع محدد.
- ترتب الفروع حسب نسبة الإكمال ثم نسبة المشاركة، ولا تستخدم عدد الأذكار الخام لترتيب الأداء.
- توفر لوحة الإدارة مكتبة تعريفات أذكار تمر بمراحل مسودة، قيد المراجعة، معتمد، ومؤرشف.
- لا ينشر تعريف ذكر قبل توثيق مرجع المصدر والمراجعة البشرية، ويعاد النص المعتمد إلى المراجعة عند تغييره.
- يفصل إنشاء الورد بين اسم الورد وتعريف الذكر؛ ويمكن إعادة استخدام الذكر المعتمد في عدة أوراد بأهداف ومدد وجماهير مختلفة.
- ينشئ الورد الجماعي تكليفات فردية للمستخدمين المطابقين للفروع والصفوف والأدوار، مع حفظ لقطة النص والهدف واحترام المدة بتوقيت دمشق.
- يدعم الورد ستة نطاقات صريحة ومتبادلة الاستبعاد: جميع المؤسسة، فرع، عدة فروع، صف، دور، أو مستخدم محدد.
- تدعم الحملات هدفًا جماعيًا للمؤسسة مع تقدم إجمالي وتفصيل مساهمة كل فرع وكل فئة مستخدم.
- يعتمد نظام النقاط على الالتزام لا عدد الضغطات: +10 لإتمام ورد، +10 لإتمام أوراد اليوم، ومكافآت عند 3 و7 و30 يومًا متتاليًا.
- تحفظ قواعد النقاط في قاعدة البيانات ويمكن تعديل قيمها أو تعطيلها دون تغيير تطبيق Flutter، مع سجل استحقاق يمنع منح الجائزة مرتين.
- يمنح النظام أوسمة «البداية الطيبة»، و«المواظب»، و«المتميز» تلقائيًا، ويتيح للإدارة منح وسام «الاستمرار» المتقدم يدويًا.
- تعريفات الأوسمة وشروطها محفوظة في قاعدة البيانات، ويظهر ما اكتسبه الطفل داخل قسم «مكافآتي».
- لا تعرض تجربة الطفل ترتيبًا أو مركزًا مقارنة بالأطفال؛ يرى إنجازه ونقاطه وأوسمته واستمراره فقط.
- تعرض لوحة المكافآت الإدارية بيانات أطفال الفرع كاملة بعد التحقق من صلاحية المدير، مرتبة بالاسم لا بالنتيجة.
- يعمل عداد الذكر دون إنترنت؛ تحفظ كل ضغطة والعملية المعلقة ذريًا في Drift قبل تحديث الواجهة.
- يستعيد التطبيق العدد وطابور المزامنة بعد الإغلاق أو إعادة تشغيل الهاتف، ويحاول المزامنة فور استعادة الجلسة وعند عودة الاتصال.
- يغطي اختبار قبول إلزامي السيناريو `20/100 → انقطاع → 30 ضغطة → 50/100 → إغلاق وفتح → مزامنة الخادم إلى 50`.
- يرصد الخادم النشاط السريع أو المرتفع ومحاولات المزامنة غير المعتادة كعلامات إدارية فقط؛ لا يحذف الإنجاز ولا يغير النقاط تلقائيًا.
- يثبت اختبار قبول MVP السلسلة من إنشاء المؤسسة وفرع دمشق والصف والطفل والذكر والورد، حتى 100 ضغطة محفوظة وظهور النتيجة في لوحتي الفرع والإدارة المركزية.

## التقنية المعتمدة

- `flutter_riverpod`: إدارة الحالة والاعتماديات.
- `go_router`: التنقل والمسارات وحماية الشاشات.
- `supabase_flutter`: المصادقة والمزامنة مع Supabase PostgreSQL.
- `drift`: قاعدة البيانات المحلية والعمل دون اتصال.
- `connectivity_plus`: رصد تغير الاتصال بوصفه إشارة لإعادة المزامنة.
- `freezed`: نماذج وحالات غير قابلة للتغيير.
- `json_serializable`: تحويل بيانات Supabase من JSON وإليه.

التطبيق مبني بـFlutter، يبدأ من Android وiOS، ويدعم العربية واتجاه RTL من البداية. تُدار الصلاحيات في Supabase عبر Row Level Security، وتظل Drift مصدر القراءة المحلي للواجهة.

## الإعداد والتشغيل

1. طبّق ترحيلات `supabase/migrations` بالترتيب، بدءًا من المصادقة ثم المؤسسات ومستخدمي الفروع وعداد الذكر وإدارة الورد ورحلتي الطفل والموظف، ثم مؤشرات لوحتي الفرع والإدارة المركزية، فمكتبة تعريفات الأذكار، ثم إنشاء الورد ونطاقاته والحملات، وأخيرًا نظام نقاط الالتزام والأوسمة وسياسة تصنيف الأطفال ومؤشرات النزاهة وفلاتر التقارير الإدارية.
2. اجلب الاعتماديات وولّد الملفات:

```powershell
flutter pub get
dart run build_runner build
```

3. شغّل التطبيق بالمفتاح العام، وليس `service_role`:

```powershell
flutter run `
  --dart-define=SUPABASE_URL=https://YOUR_PROJECT.supabase.co `
  --dart-define=SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

يدعم التطبيق مؤقتًا `SUPABASE_ANON_KEY` للتوافق، لكن `SUPABASE_PUBLISHABLE_KEY` هو الاسم المفضل.

## الأدوار

- كل حساب جديد يحصل على دور `member` من Trigger داخل قاعدة البيانات.
- لا يستطيع تطبيق Flutter تغيير حقل `role`.
- يمنح دور `admin` فقط عبر بيئة موثوقة مثل لوحة SQL أو خادم يستخدم `service_role`.
- التوجيه حسب الدور في Flutter ليس بديلًا عن سياسات RLS.

## إدارة المؤسسات

- ينشئ المدير مؤسسة ويصبح `owner` لها تلقائيًا.
- لا يستطيع المدير إدارة مؤسسة أخرى ما لم تكن له عضوية `owner` أو `admin` فيها.
- تتبع الفروع مؤسسة واحدة، وتتبع الصفوف فرعًا واحدًا، ويتبع كل مستخدم فرعًا واحدًا.
- الطفل والمعلم يتبعان صفًا واحدًا؛ الإداري ومدير الفرع لا يرتبطان بصف.
- ربط سجل الموظف بحساب Supabase اختياري ومحمي، ولا يستطيع تطبيق Flutter تعيينه.
- الحذف من الواجهة حذف ناعم يحفظ العلاقات التاريخية.
- عمليات CRUD الإدارية في المرحلتين الثالثة والرابعة تتطلب اتصالًا بـSupabase؛ التخزين دون اتصال مخصص لاحقًا للمسارات اليومية.

## عداد الذكر

- لا يتضمن التطبيق نص ذكر عامًا أو هدفًا تعبديًا مولدًا؛ يكتب المستخدم عنوانه الخاص ويحدد الهدف.
- تظهر الزيادة محليًا فورًا حتى دون اتصال، وتبقى العمليات المعلقة محفوظة بعد إغلاق التطبيق.
- `connectivity_plus` يحفز إعادة المحاولة فقط؛ نجاح RPC هو الدليل الوحيد على اكتمال المزامنة.
- وجود عمليات معلقة عند تشغيل التطبيق يحفز محاولة مزامنة مباشرة حتى إن لم يصل حدث اتصال جديد.
- يبدأ عداد جديد بعد اكتمال الحالي، مع الاحتفاظ بالسجل المحلي السابق.
- يرتبط العداد الناتج عن تكليف إداري بمعرف الورد، وتتحقق RPC من حساب الطفل قبل قبول كل زيادة.

## مبادئ المنتج

1. الخصوصية أولًا؛ لا تُجمع بيانات لا يحتاجها المنتج.
2. تجربة هادئة بلا عناصر تنافسية أو إشعارات مزعجة.
3. اللغة العربية وRTL جزء أصيل من التصميم وليسا إضافة لاحقة.
4. أي نص ديني معروض داخل المنتج يجب أن يكون من مصدر موثوق ومراجع.
